Diamond — OSS Repo Research

Session date: 2026-05-18 · Companion to diamond_Build/3-Build-Plan.md → OSS Repo Research section

1. Bottom line

No single open-source repo does all three jobs (image generation, video generation, scheduling) at the level of polish that commercial tools or Diamond's specialized direction warrant. The mature OSS leaders each pick one job and do it well.

The realistic move for Diamond is not to adopt any of these wholesale — Diamond is already mature and architecturally different from Postiz (Diamond uses visible-browser automation; Postiz uses official OAuth APIs). Instead, mine specific features from each source with full awareness of license constraints.

3. Insight: AI flips the copy/reimplement tradeoff

Copyright protects code expression, not the underlying concept or algorithm. With AI, the cost of "read it, understand it, write it in your own stack" has collapsed from weeks to hours. This changes the calculus on which features are worth adopting:

What used to be a "build from scratch vs. fork an existing repo" decision is now a "spend an afternoon reimplementing the idea you saw" decision.

For GPL/AGPL sources (Postiz, ComfyUI), this is the unlock: read the public source for concepts and write your own implementation in Diamond's JavaScript/Electron stack. Clean-room reimplementation has been legally fine since the 1980s — AI just made it cheap.

For MIT/Apache/BSD sources (tiktoka-uploader, publora/skills), you can lift code directly with attribution, but reimplementation in Diamond's stack is usually faster than porting Python.

4. Insight: the model is the moat, not the wrapper

Initial framing was "embed ComfyUI." Better framing:

The model is the moat, not the wrapper. Pick the API that gives you the quality/cost ratio you want and have Diamond be the orchestration layer.

Diamond should be the layer that knows:

  • Which prompts to send (with brand voice, campaign context, claim library applied)
  • Which provider to call (Replicate, Runway, Luma, Pika, fal.ai, Modal, or self-hosted ComfyUI)
  • What to do with the result (asset library, approval queue, scheduling)

This keeps Diamond modular: swap generation backends without rewriting Diamond. License-clean: calling a separate service is "aggregation," not derivative work. Cost-aligned: pay-per-generation economics scale with usage.

6. Survey 1 — ComfyUI

StatValue
Stars / Forks113,302 / 13,270
LicenseGPL-3.0
ActivityActive development
CapabilitiesImages, video, 3D, and audio via custom nodes

Architecture

Ships with a proper HTTP server (server.py, 55KB) and an api_server/ module containing routes, services, utils. Designed to run as a service, not embedded.

Integration pattern (recommended)

  1. Run ComfyUI as a separate backend — local (with a GPU) or hosted (RunPod serverless ComfyUI ~$0.0004/sec, Replicate, Banana, Modal).
  2. Diamond stays in JavaScript/Electron — adds a generative-worker.js alongside the existing Playwright browser-worker that POSTs workflows to the ComfyUI HTTP endpoint and polls for results.
  3. Workflow JSONs become assets — store ComfyUI workflow JSON files in Diamond's asset library, parameterize the text prompts, run them on demand. This is how everyone integrates ComfyUI: the workflow is a graph saved as JSON, POSTed with parameter overrides.
License safety
GPL-3.0 means if you embed ComfyUI's code, your tool becomes GPL. But calling a separately-running ComfyUI over HTTP is fine — that's "aggregation," not derivative work. Same model as calling Postgres or Redis. Diamond stays MIT/private.

Commercial alternatives (no GPL concern, pay-per-generation)

  • Runway — best for video, $$$
  • Luma Dream Machine — video, more affordable
  • Replicate — runs ComfyUI workflows on demand, pay-per-run, ~$0.001–$0.05 per image
  • Modal — host your own ComfyUI workflow as a function
  • fal.ai, Pika, Banana, others

Diamond impact estimate

New generative-worker module + asset-library schema additions for "workflow templates" and "generated outputs" + a UI affordance in the draft flow. ~1–2 weeks of focused work.

Approach

Uses Selenium with two authentication modes:

  • SessionId-based — pass an existing TikTok session cookie

File structure

test-tiktok-manual-sessionId.sh

What's mineable for Diamond

  • TikTok upload selectors and DOM dance — the specific CSS / XPath selectors for TikTok's upload form, captcha handling, scheduled-post flow. This is the brittle stuff that takes hours to figure out from scratch.
  • Session cookie strategy — Diamond currently uses Playwright browser profile isolation; this repo's sessionId mode is an alternative for cases where the profile is unreliable.
  • YouTube upload flow — they also have a YouTube uploader; might inform Diamond's YouTube Shorts work.
License safety
MIT — you can lift specific functions and selectors directly into Diamond's tiktok-adapter.js, as long as you preserve the original copyright notice somewhere (typically a NOTICES file or a top-of-file comment block).

Diamond impact estimate

Probably 2–3 days to port the upload flow and adapt to Playwright's API (Diamond uses Playwright, not Selenium). The win is mostly in the selectors and edge-case handling that took the original author months to figure out.

StatValue
Stars30,265
LicenseAGPL-3.0

Critical architectural difference
Postiz uses each platform's official OAuth API (X API, IG Graph API, LinkedIn API, etc.). Diamond explicitly went the opposite direction — avoid platform APIs, use visible browser sessions. Postiz's integration code is not directly transferable to Diamond's approach.

So Postiz can only inform Diamond on surface features and UX patterns, not under-the-hood integration.

Top concept-level steals

  1. AI prompt-templates in the draft flow. Postiz bakes "AI write me a tweet about X" into the draft view. Diamond has the building blocks (brand voice, claim library, content pillars) but no UI affordance that says "generate a draft from this campaign slot using these constraints." Worth adding.
  2. Analytics visualization. Diamond logs the data; chart it. Use Chart.js or Recharts (both MIT) — no need to look at Postiz code at all for this; just steal the idea that metrics should be visualizable, then implement with off-the-shelf chart libs.
  3. Webhook-out for external automation. Diamond has the Polaris bridge but no generic "POST to a user-configured webhook on event X" mechanism. Useful for connecting Diamond into Zapier/Make if you ever want that.
License safety
AGPL-3.0 is aggressive. Even running Postiz over a network triggers the share-alike requirement (that's the "Affero" part — it closes the SaaS loophole that vanilla GPL leaves open). So don't look at Postiz's source code while writing Diamond features. Read the public docs, screenshots, and UX patterns only. Implement from concept, not from code. Keep your reading documented (a docs/research/postiz-features-observed.md is fine; copying any code into Diamond is not).

Diamond impact estimate per concept

  • AI-in-draft UX = ~3–5 days
  • Analytics dashboards = ~1 week (mostly chart UI + data shaping)
  • Webhook-out = ~1–2 days

If picking just one
The single biggest capability gap is AI image and AI video generation. Diamond renders structured templates (leaderboard cards, prize cards, etc.) but doesn't appear to do generative AI for hero images, lifestyle shots, or short-form video. That's where social-content quality gates have moved. The integration is architecturally clean — it's another worker, like Playwright is for browser staging.

10. License discipline going forward

  • When mining a GPL or AGPL repo for ideas, document the concept in a docs/research/<source>-features-observed.md file rather than letting the source code itself sit in Diamond's working tree. The research file becomes the input to fresh implementation.
  • For MIT/Apache/BSD sources where code is lifted directly, preserve attribution — either in a top-of-file comment block on the adapted file, or in a project-level NOTICES file.
  • Diamond's own license stays clean as long as: GPL/AGPL code never lands in the working tree, only concepts do; MIT code that lands carries its required attribution.
